# DSH Mobile 项目方案：本地优先的主动型个人 Agent 运行时

> 状态：2026-11-01 · 基于 rc.189 现状与已确认的产品方向（Step 1–5 已落地，Step 6 起待做）
> 这份文档回答一个问题：**我们和普通助手、普通 harness、Muse、Grok bot 到底哪里不一样，以及这件事怎么真实落地。**

## 1. 一句话定位

**装在手机里的本地优先 Agent 运行时 —— 手机本身就是工作站：对话是驾驶舱，异步工作有实体、有证据、有唤醒策略；连电脑只是同一局域网里的补充入口，不是云端，也不是支柱。**

不是「一个更聪明的聊天窗口」，也不是「把桌面 CLI 缩到手机上」，更不是「电脑的遥控器」。它要同时做到三件普通产品做不到的事：

1. **真的去做**：任务、定时、团队都是可执行的工作，不是一段回复 —— 而且**不接任何电脑、不在局域网里也能做完**；
2. **做完会回来**：工作的开始、阻塞、完成都有可见状态和明确的唤醒策略，不静默；
3. **每一件都能查**：谁触发、批准了什么、做了什么、结果在哪，都有证据链。

## 2. 和普通助手 / 普通 harness / Muse / Grok 的差别

| 维度 | 普通助手 | 普通 harness（桌面/CLI） | Muse（Meta） | Grok bot | **DSH Mobile** |
|---|---|---|---|---|---|
| 主入口 | 聊天框 | 终端 / IDE | 聊天 + 角色 | 聊天 + 人格 | **对话即驾驶舱** |
| 执行位置 | 厂商云 | 用户电脑 | 每用户云 VM | 厂商云 | **手机本地（自带工作区与算力）** |
| 异步工作 | 基本没有 | 有，但绑进程/终端 | 有，云端常驻 | 弱 | **有，持久 Mission + 可恢复** |
| 主动性 | 被动问答 | 无 | 强（常驻/后台） | 强（人格/在场） | **强，但必须可解释** |
| 设备能力 | 有限 | 无 | 通过云侧 API | 有限 | **手机原生：通知、文件、设备控制、语音、安装** |
| 数据归属 | 厂商 | 用户 | 厂商 VM | 厂商 | **用户设备；不上云同步** |
| 权限/证据 | 弱 | 日志 | 云端审计/Sentinel | 弱 | **Mission 级权限 + 本地证据/审计** |
| 中断恢复 | 无 | 进程结束即结束 | 一直在 | 无 | **账本持久化、启动补偿、诚实标记 interrupted** |
| 扩展性 | 插件少 | 强 | 连接器生态 | 弱 | **Harness 插件/工具 + 多模型端点** |

**不跟 Muse 拼云端常驻和连接器数量，也不跟 Grok 拼人格热度。** 我们学 Muse 的「托付感」——后台执行、敏感操作确认、操作留痕；学 Grok 的「在场感」——语音与主动开口；但把两者都落在**用户自己的设备**上，并用「对话里的 Mission」把它们收口。

## 3. 目标体验

用户说：

> 把昨晚的构建和今天的巡检整理成一版报告，18:00 前发我。

产品应该发生的事：

1. 对话里出现一条 **Mission 卡**：来源（后台/定时）、状态、下一步、证据入口；
2. 用户锁屏、切走、甚至把 App 杀掉，任务继续（在平台允许的范围内），状态在账本里；
3. 任务完成 → 按唤醒策略回到对话：当前会话空闲就直接开一轮；忙就排队；App 不在就通知；用户回来能补上；
4. 用户点开卡片，能看到「谁触发、用了哪个工具、产出了什么、批准过什么」；
5. 下一次用户再说一句话，Agent 已经带着这段工作上下文继续，而不是从零开始。

四个承诺，按重要性排序：

- **说一句，它真的去做**（执行，而不是只给建议）
- **做完会回来**（唤醒可见，不静默）
- **每一件都能查**（证据与权限）
- **锁屏、断网、换设备也不丢**（持久与恢复；不承诺永远在线）

## 4. 产品原则（不可妥协）

1. **单一事实源**：Mission 状态只在内核账本里，前端不各自推导、不维护第二套通知队列。
2. **无静默状态**：任何异步事件要么产生 Mission 状态迁移，要么显式进入唤醒队列；不允许「系统里有、界面没有」。
3. **唤醒显式**：`idle-auto / queue / notify / defer` 四档，策略可读；`idle-auto` 只用于当前会话且空闲。
4. **信任绑定 Mission**：默认沿用会话权限，Mission 只能收窄；危险操作确认与证据都挂在具体这件事上。
5. **对话是唯一控制面**：任务页只是账本索引，不新增「Mission 中心」一级页面。
6. **本地优先 = 手机自己就是工作站**：状态、记忆、执行、审计、产出都留在设备；模型走用户自己的端点。不引入云同步/服务端记忆/托管连接器，也不依赖任何第三方中继。连电脑只是**同一局域网内的可选补充**，做不到就当它不可用，不假装在跑。

## 5. 能力地图：为什么「更强」

### 已经具备的底座（rc.187）

- **执行**：165 个工具（文件/命令/设备控制/App 构建安装/图像视频/搜索/`http_request` 等），本机内核 + 沙箱 + 权限闸门；手机内可完成打包安装 App、跑终端会话、处理文档与音视频。
- **异步**：后台 Job、定时任务、团队/子代理；前台服务 + WakeLock + 完成通知 + 持久唤醒队列。电脑 Link 是**同一局域网直连**的补充入口（中继做不了，不承诺远程）。
- **连续性**：本地会话、记忆、语音输入（端侧识别）/输出（内置音色 + 系统兜底）、锁屏通知、恢复后补发。
- **主动性**：陪伴式畅聊、空闲自动唤醒、定时到点唤醒、完成通知唤醒（rc.181 已修「到点无响应」）。
- **信任基础**：会话级权限、危险动作确认、`NetPolicy`（公网明文拦截）、本地数据；Mission 卡、进行中带、详情抽屉与证据导出（rc.182–rc.187）。
- **工程底座**：556 个 JVM 单测、16 条 web 回归、lint/static/release 门禁；本地优先的发布链。

### 目标态新增

- **Mission Ledger**（已落地 rc.184）：统一 jobs/schedules（后续 team/pc）的持久账本与状态机。
- **Wake Router**（已落地 rc.186）：统一唤醒策略与平台适配，去掉 job/schedule 各自的通知分支。
- **Mission 级权限与证据**（已落地 rc.187）：可回看、可导出、审批作用域到具体这件事。
- **工作站底座**（下一步）：工作区容量与落点统一、长任务可重跑、离线与额度不可用时的诚实降级、各类本地数据的体积上限与清理。
- ~~桌面作为自有算力（委托重/长任务给电脑）~~ **取消**：网络中继无法完成，只剩同一局域网直连，场景过窄；算力方向改为把手机端本身做扎实。

## 6. 目标架构

```
触发：用户 / Agent 工具 / 时间 / 团队 /（可选）局域网内的电脑
                 │
                 ▼
Mission Ledger（本地持久 · 状态机 · 来源 · 证据 · 唤醒策略）
                 │
                 ▼
Wake Router（idle-auto / queue / notify / defer + 前台服务/闹钟/开机补偿）
                 │
                 ▼
执行：Agent 回合 / 后台 Job / 定时任务 / 团队 ｜（可选）局域网直连电脑
                 │
                 ▼
呈现：对话 Mission 卡 · 进行中带 · 任务页索引 · 通知深链
```

### Mission 最小模型

- `id`、`kind`（job/schedule/team/pc）、`sourceId`、`sessionId`
- `title`、`state`（queued/running/waiting/settled）、`outcome`（done/failed/cancelled/interrupted）
- `origin`（user/tool/schedule/team/pc + turnId/toolCallId）
- `wakePolicy`（idle-auto/queue/notify/defer）
- `evidence[]`（job 输出、schedule 投递、deliverable、关键 tool/result）
- `permissionScope`（继承会话，可收窄）
- 时间戳与 `dedupeKey`；`waiting` 只用于权限/用户输入等闸门

设计要点：**先有账本，再有路由，再有权限/证据**。顺序反了就会重新长出三套通知。

## 7. 分阶段落地（每一步都能单独验收）

### 已完成基线（rc.181–rc.183）

- rc.181：定时任务到点真正发起一轮；持久唤醒 + 系统通知；更新镜像替换。
- rc.182：对话 Mission 卡（玻璃 + 抠图毛绒）、进行中带、任务页筛选；`job_start`；前端投影。
- rc.183：输入框原生滚动条移除。

### Step 1 · Mission Ledger v1（jobs + schedules） · 已落地 rc.184

把前端投影换成内核账本；对话卡、进行中带、任务页读同一份数据。

- 新增 `kernel/mission/Mission.kt`、`MissionStore.kt`、`MissionRegistry.kt`；JSONL + 原子索引；进程死亡恢复为 `interrupted`，不假装 running。
- `JobRegistry.onStart/onDone`、`ScheduleRegistry` 的 create/update/delete/fire 同步 upsert。
- `KernelBridge` 暴露 `missionList/get/cancel/evidence`；前端双读一个版本（Ledger 优先，旧投影回退）。
- 验收：起 job 即时出现；定时到点状态一致；杀进程再开可恢复；切会话不串；无重复卡。

### Step 2 · 统一唤醒层（Wake Router） · 已落地 rc.186（真机验证 rc.186）

- 一条路由消费 Mission 状态迁移；`idle-auto/queue/notify/defer` 落成可执行策略；持久 wake 记录，`missionId + transition` 去重。
- job/schedule 各自的通知分支退场；agent pre-step 读统一队列。
- 验收：空闲/忙碌/后台/杀进程四种场景都「只唤醒一次」；后台回来能补一轮；远期定时不打扰。
- 真机（模拟器 dsh36 + rc.186 debug）已过：杀进程重开补一轮且不重复、跨会话不串、忙碌排到本轮结束、进程死在任务中途诚实标 `interrupted` 且不产生唤醒。
- **残余**：内核只在 `eventSink == null` 时发系统通知，因此「App 退到后台但进程还活着」这一路只有队列、没有通知。修法已定：Activity `onPause/onResume` 写一个 `appVisible` 标志，通知条件改成 `eventSink == null || !appVisible`。属于本步收尾，未排进 Step 3。

### Step 3 · Mission 级信任与证据 · 已落地 rc.187

- `AgentConfig` 带 `missionId / wake / wakeId`；`effectivePermission(session, mission)` 把权限**只收窄**地合进沙箱与工具 Gate；审批卡显示所属 Mission，「始终允许」在那件事里落 `grants`，不写会话级免问表；决定进 `approval/decided` 日志与 Mission 证据。
- 证据索引从 SessionStore（`tool/call`、`tool/result`、`user/message`、`deliverables/presented`）/ JobJournal / 唤醒队列按引用现取正文；卡片「查看」就地开抽屉，`missionExport` 导出 JSON/Markdown 到工作区。
- 验收对齐：**原计划写的「readonly Mission 无法写文件；需要写时弹出 Mission 级确认，批准后才执行」与安全纪律冲突** —— 只读档是硬拒，批准不能把它软化成可执行（rc 早期就踩过「只读下 run_code 变成点一下就能跑」）。因此这条改成：只读的 Mission 硬拒写操作并保持拒绝；Mission 级确认用在 `ask/default` 档的危险动作上，批准范围只覆盖这一件事。其余验收（证据可回看/可导出/重启仍在、审批不泄漏）按原样通过。

### Step 4 · 工作站底座（手机端就能扛住重活） · 已落地 rc.188

判断标准：**一台手机、不连电脑、不在局域网**，也能把一件重活做完、做完能查、断电不丢。

- 工作区容量与落点统一：spill / 交付物 / 导出 / undo 存档都在模型与用户可读的工作区里（收掉 `TODO(spill)`），容量占用可见。
- 长任务本地扛得住：前台服务与 WakeLock 策略复核；`origin` 留住工具与参数，被回收的 Mission 才谈得上「重新跑一次」。
- 离线与降级诚实：端点不可达 / 额度耗尽 / 无网时，排队或明确不做，不显示成「进行中」。
- 数据边界：记忆、会话日志、输出环、账本、唤醒队列的体积上限与清理统一成一份。
- 验收：长任务中途锁屏与杀进程各一次都能续上并回看；离线时它明确说不做。

### Step 5 · 团队合流（本地） · 已落地 rc.189

- 成员任务创建/汇报/完成 → Mission（kind=team，origin 带成员名）；任务页来源增加「团队」；证据与抽屉沿用 Step 3。
- 验收：成员汇报在任务页与对话卡是同一条；唤醒不串会话；成员被中断时诚实标 `interrupted`。

### Step 6 · 连电脑（缩成一个局域网小点）

- 现实：网络中继无法完成（无可部署且可自证可信的中继，公网入口又必须 https），只有同一局域网直连可用。
- 做法：界面说实话 —— 不在同一网络就是「未连接」，不进进行中；连上时电脑会话结果进 Mission（来源「电脑（局域网）」），完成走同一 Wake Router。
- **委托重/长任务给电脑：移出计划**。等真有用户自己可信的远程通道再评估。

### Step 7 · 收尾

- Step 2 残余：App 在后台但进程存活时不发系统通知（判定只看 `eventSink == null`）→ 用 `appVisible` 修掉。
- Mission 更新只 patch 卡片节点，不整表重建；性能与玻璃观测。
- 新增 `docs/mission-ledger.md`（模型/状态机/唤醒/证据）；README 同步；清理 rc.186 后已失效的旧 notices 基础设施；旧路线文档不混入新方向。

## 8. 可行性依据与硬约束

### 已经证明可行的部分

- 后台任务/定时任务/团队/语音/通知已有真实实现，不是从零开始；手机内打包并安装 App、跑持久终端会话、处理文档与音视频都已实测通过 —— 「手机当工作站」不是设想，是已经跑通的部分。
- rc.181 已证明「到点 → 唤醒 → 发起一轮」在全链路可行；rc.182 已证明 Mission 卡/带能按会话实时更新。
- 本地账本可以沿用 `ScheduleStore`/`JobRegistry` 已验证的原子写盘方式。

### 必须如实承认的边界

- **没有 7×24 常驻**：Android Doze、ROM 杀进程、厂商省电限制；我们卖「随时接得上」，不卖「永远在线」。
- **准点精度是近似**：不承诺 exact alarm；错过的任务在下次启动/唤醒时补。
- **执行体不跨进程**：Job 执行本身在进程内；账本持久化，进程死亡后标记 `interrupted`，不伪造完成。
- **连电脑只有局域网这一条路**：不在同一网络就是不可用；不承诺远程委托，也不把「未连接」说成「等待中」。算力主路径是手机本地。
- **模型是用户端点**：本地只跑 ASR/TTS 等小模型；能力上限取决于用户选的模型与网络。

### 对应的缓解

前台服务 + WakeLock + 开机补偿 + 持久队列 + 启动恢复 + 显式 `waiting/notify/defer` + 真实状态文案。每一条都要有回归守卫，防止「看起来很智能，实际是静默失败」。

## 9. 评估指标（可测，不看虚荣数据）

- **可见性**：异步工作开始后 1s 内出现 Mission 卡/带的比例；静默状态事故 = 0。
- **唤醒可靠性**：只唤醒一次率；重复唤醒率；杀进程后补唤醒成功率。
- **恢复**：`interrupted` 标记准确率；错过任务补偿率。
- **信任**：危险动作确认覆盖率；证据可回看率；审计导出成功率；审批泄漏 = 0。
- **体验**：卡片更新是否只重绘自身；进行中带是否影响输入/滚动；明暗主题下材质一致性。
- **差异化**：无需用户二次催促就完成的工作占比；锁屏后仍完成并回到对话的占比。

## 10. 非目标与边界

- 不做云 VM、账号同步、服务端记忆、托管连接器。
- 不承诺 7×24 常驻或准点唤醒。
- 不新增「Mission 中心」一级 tab，不重做现有视觉与工具行。
- 不复活旧 harness 路线（WorkManager/PTY/exact alarm 等）；旧审计项只在新目标下重新评估。
- 不替用户做不可逆的敏感操作：确认与审计是产品的一部分，不是补丁。

## 11. 与 Muse / Grok 的关系（一句话）

**Muse 证明「个人 Agent 的价值在托付」，Grok 证明「在场感能建立关系」；DSH Mobile 用一台自带工作区的手机 + 可审计的 Mission，把两者落在用户自己手里 —— 不靠云，也不靠旁边那台电脑。**

## 12. 下一步

从 **Step 1（Mission Ledger v1）** 开始：先把 jobs/schedules 从前端投影升级为内核账本，其余不动；完成、验收、出一个 rc 包，再进入 Wake Router。实施细节以当前迭代计划为准，产品方向以本文为准。
